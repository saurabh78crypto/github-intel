# GitIntel

> **AI-powered GitHub profile intelligence** - see your profile through a recruiter's eyes.

GitIntel analyzes any public GitHub profile and produces a structured recruiter-signal report: scores across five hiring dimensions, matched skills, skill gaps, strengths, weaknesses, and actionable suggestions - all generated by a local LLM pipeline in real time.

---

## Why It Was Built

Developers often can't tell whether their GitHub profile actually communicates their skills to hiring managers. A profile with 200 repositories can still read as scattered or low-signal, while a profile with 10 well-documented projects can look exceptional.

GitIntel was built to answer a single question: **"What would a senior technical recruiter conclude from this profile in the first 60 seconds?"**

The tool bridges the gap between writing code and presenting code - giving developers a concrete, actionable baseline they can improve.

---

## Features

- **Real-time analysis** via WebSockets - live progress updates as each pipeline stage runs
- **Recruiter-signal scoring** across five dimensions: Activity, Depth, Breadth, Communication, and Impact
- **Role-targeted reports** - analysis is tuned to a chosen target role (Full Stack, Backend, Frontend, ML, DevOps)
- **Skill matching & gap detection** against the target role
- **Actionable suggestions** for specific repos and profile improvements
- **Shareable reports** - every report has a public permalink
- **Analysis history** - authenticated users get a personal dashboard of past reports
- **Anonymous use** - reports are saved and accessible without an account; login just adds history

│                 │                               │  WS Gateway          │

                                                  ┌──────────────────────┐
                                                  │  FastAPI AI Service  │
                                                  │  (8001)              │
                                                  │                      │
                                                  │  Scraper → Embedder  │

The frontend never talks directly to the AI service. All WebSocket traffic is proxied through the NestJS gateway, which handles authentication, persists completed reports, and relays progress events to the browser.

## AI Pipeline

Each analysis request triggers a five-stage pipeline:

```
1. SCRAPING      GitHub API → profile + up to 50 repos + READMEs (top 20)
2. EMBEDDING     sentence-transformers → per-repo vector documents → ChromaDB
3. SCORING       RAG query → Qwen2.5-7B → JSON score breakdown (5 dimensions)
4. REPORT        RAG query → Qwen2.5-7B → full intelligence report (JSON)
5. COMPLETE      Report saved to DB → client redirected
```

ChromaDB collections are **temporary per analysis** - created at the start of each request and deleted in a `finally` block. This keeps memory use flat regardless of concurrent analyses.

RAG retrieval is used rather than stuffing all repo data into a single prompt. The scoring step queries for technically complex repos; the report step queries for repos most relevant to the target role. This improves output quality and keeps token counts manageable.

### LLM Design Decisions

- **Qwen2.5-7B-Instruct** was chosen for its strong instruction-following and JSON output reliability at a size that runs cost-effectively on Hugging Face Inference.
- Both LLM calls use `temperature: 0.1` and `response_format: { type: "json_object" }` to maximize structured output consistency.
- `safe_json_parse` strips markdown fences before parsing, handling models that wrap JSON in code blocks despite instructions not to.
- Scoring and report generation are **separate LLM calls** with separate RAG retrieval queries - this separation keeps each prompt focused and produces more reliable results than a single mega-prompt.

## Data Model

```
User
├── id (UUID)
├── email (unique)
└── password (bcrypt, 10 rounds)

Analysis
├── id (UUID)
├── username
├── targetRole
├── report (JSONB - full AI output)
├── overallScore
├── isPublic
├── user → User (nullable, for anonymous reports)
└── createdAt
```

Reports are stored as JSONB so the full AI output is preserved without a rigid schema. `overallScore` is denormalized for fast dashboard queries.

---

## Authentication

- Cookie-based JWT (`HttpOnly`, `SameSite: lax`, 7-day expiry)
- The NestJS `JwtStrategy` extracts the token from `req.cookies.token` - **not** the `Authorization` header - so it works seamlessly with both REST and WebSocket connections
- The WebSocket gateway reads the same cookie from the socket handshake headers to associate analyses with user accounts
- **Anonymous use is fully supported** - reports are saved without a user FK; logging in just enables the history dashboard

## Getting Started

### Prerequisites

- Node.js 20+
- Python 3.11+
- PostgreSQL (or a hosted Postgres URL)
- A Hugging Face account with a token that has access to the Inference API
- *(Optional)* A GitHub personal access token to increase API rate limits

### 1. AI Service

```bash
cd ai-service
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt

# .env
HF_TOKEN=hf_...
GITHUB_TOKEN=ghp_...   # optional but recommended

uvicorn main:app --host 0.0.0.0 --port 8001
```

The service pre-loads the embedding model at startup. First launch will download `all-MiniLM-L6-v2` (~90 MB).

### 2. API (NestJS)

```bash
cd api
npm install

# .env
DATABASE_URL=postgresql://user:pass@host:5432/gitintel
JWT_SECRET=your-secret-here
AI_SERVICE_URL=ws://localhost:8001/analyze
NODE_ENV=development

npm run start:dev
```

TypeORM `synchronize: true` will create tables automatically on first run.

### 3. Frontend

```bash
cd web
npm install

# .env.local
NEXT_PUBLIC_API_URL=http://localhost:3001/api
NEXT_PUBLIC_SOCKET_URL=http://localhost:3001

npm run dev
```

Open [http://localhost:3000](http://localhost:3000), enter a GitHub username, and run an analysis.

## Key Design Decisions

**Why three separate services?**
Separating the AI pipeline from the API backend means the Python service can be scaled, swapped, or restarted independently without affecting auth or data persistence. It also keeps Python's ML dependency footprint out of the Node.js process.

**Why WebSockets for analysis?**
Analysis takes 15–30 seconds. A long-polling REST call would be a poor UX. WebSockets let the pipeline emit granular progress events (scraping → embedding → scoring → report) that map to a real-time progress ring in the UI.

**Why RAG instead of full-context prompting?**
A developer with 50 repos would produce ~75k tokens of context if everything were included. RAG keeps each LLM call focused and within a reasonable context window while selecting the most semantically relevant repos for each specific question (scoring vs. role-fit report).

**Why cookie-based auth instead of Bearer tokens?**
Cookies are automatically attached to same-origin WebSocket upgrade requests and all API calls, eliminating the need to manually manage token headers in both the REST client and the socket.io connection configuration. `HttpOnly` cookies also prevent XSS token theft.

**Why ChromaDB in-memory with per-analysis cleanup?**
Persisting vector data across analyses provides no benefit - the embeddings are only queried twice per analysis and are never needed again. In-memory ChromaDB with explicit cleanup keeps the service stateless and avoids disk I/O.
